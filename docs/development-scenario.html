Claims Intake Triage

How a synthetic-data insurance POC went from a discovery conversation to a privacy-minimized, deterministic triage system — thirteen commits, three architecture course-corrections, and one rule that survived every rewrite: Claude extracts facts, code makes the call.

This is the full build history, reconstructed from the session transcript and the git log — including the parts that didn't make it into any commit message: the false starts, the plan that got rejected, and the bugs a clean environment surfaced that a working laptop had been quietly hiding.

00

Before there was a plan

The very first two prompts weren't about insurance at all — a generic "analyze this codebase and write a CLAUDE.md" and an "explore this repository" request, the default way of orienting inside an empty repo. Both were superseded within minutes once the actual brief arrived: a training POC called Insurance Underwriting & Claims Triage, scoped tightly from the start — Python 3.11+, synthetic data only, no LLM inference in the first cut, an explicit Explore → Plan → Implement → Verify → Diff workflow for everything that followed.

That guardrail file was committed before a single line of application code existed.

01

Discovery, before code

Before proposing any solution, a personal reusable skill — /discovery — was built: an eight-question business-requirements interview. It was run once, in full, against this exact problem.

Process

Adjusters read unstructured FNOL emails and call notes, identify policyholder, incident, loss and documents, then build a case summary and next step by hand.

User

Claims intake specialists and adjusters — domain-competent, burdened by repetitive reading and data entry.

Manual effort

~15–20 minutes per case; hundreds to thousands of cases a month.

Business pain

Repetitive work, inconsistent summaries, delayed routing, missed document requests — senior adjusters pulled off complex claims.

Available data

Synthetic emails and call notes for the POC; production would pull from email, CRM, policy admin, document repositories.

Risks

Wrong extraction, missing fields, PII exposure, misrouting — and explicitly: must not make coverage, liability, fraud, or payment decisions. A human stays accountable.

Success metric

Less prep time, higher field completeness, correct review-flagging. ROI = minutes saved × case volume × loaded staff cost.

Time limit

A working POC inside about an hour, on a small synthetic set.

Risk answer #6 is worth holding onto — the system must not make coverage, liability, fraud, or payment decisions — because it is the exact line that gets re-litigated, in code, three phases later.

02

The plan gets rejected

The first plan built from that discovery was a deterministic, regex-and-heuristics baseline — safe, and exactly what the original CLAUDE.md asked for. It was turned down on the spot:

Do not implement this plan yet. This is a useful deterministic baseline, but it does not demonstrate an AI-assisted workflow because it uses only regex and heuristics. Please revise the plan into two explicit stages: Stage 1 — Baseline: deterministic extraction and routing, synthetic cases and tests. Stage 2 — AI-assisted POC: the smallest safe way to use Claude for extracting structured fields.Plan review — rejection of the pure rule-based approach

Two more rounds locked the architecture down before anything was built: credentials would live in a local .env, never in the Claude Code shell environment (a Pro-subscription workflow, not an API key export); extraction had to use real Structured Outputs (output_config.format with a JSON schema) — never "ask the model to return JSON" and hope.

Then, scope was cut hard — back down to a single pipeline:

Let's reduce scope before implementation. Build one minimal end-to-end POC only: synthetic claim text → Claude Structured Output extracts the fixed fields → deterministic missing-field check → terminal summary with "human review required". Do not build Stage 1 baseline, routing logic, evaluation report, follow-up drafting, config.json, or comparison files.Scope reduction — down to seven files

The two-stage evaluation framework was never built. Looking back at the discovery answers, it didn't need to be — the success metric was completeness and correct flagging, not a side-by-side benchmark. The cut tracked the actual requirement.

Language discipline

"Ready" is not a safe word

2026‑09‑12

A wording-only pass replaced every terminal status that said "ready" or "ready to process" with an explicit "all mandatory fields present — human review required." Small change, but it's the first appearance of a rule that resurfaces later at a much larger scale: the system's own language must never imply more autonomy than the code actually has.

Architecture fight

The high-value flag saga

2026‑09‑13

A high-value rule was added the obvious way: ask the model to set high_value_flag when loss exceeded a threshold, raised from $10,000 to a realistic $100,000. Near the boundary the flag came back inconsistent — because the model had quietly been handed a judgment call, not a fact to extract. That's exactly what discovery risk #6 had warned against.

The fix was architectural, not cosmetic: high_value_flag was removed from the Claude schema and the required-fields list entirely. Python now recalculates it deterministically, after extraction, every time — closing a companion bug where if estimated_loss: had been silently treating a real $0 claim as missing data. Three edge cases were then locked in as regression tests: the exact $100,000 boundary, a genuine $0 loss, and a case with the loss field missing outright.

Governance

Three trace schemas, then a rebuild

2026‑09‑13

To make every run auditable, three trace-schema shapes were weighed — a flat record, a layered record, an append-only event stream — framed explicitly as an EU AI Act–inspired auditability pattern, not legal compliance. The layered schema won on clarity and effort. The first build of it overreached: claimant name, policy number and contact details went into the trace files as raw text. Caught in review before commit, it was rebuilt privacy-minimized — field presence status only (present / null / missing), loss reduced to a bucket (zero, 1_to_100k, over_100k, missing), input hashed rather than stored.

A second, subtler defect followed the same review discipline: the documentation called the trace files "immutable," while the code underneath simply wrote plain JSON to disk. Wording only — "per-run audit records," not immutable ones — was corrected in both the README and the docstring, with zero logic touched.

Clean-room proof

A fresh venv found what the laptop hid

2026‑09‑13

The README never mentioned activating a virtual environment — a real onboarding blocker, flagged directly. Verifying the full setup path in a genuinely fresh venv surfaced something worse: requirements.txt pinned anthropic==0.45.0, a version that doesn't even have the output_config parameter the whole extraction path runs on. It worked locally only because the working directory's own environment had long since drifted ahead of the pinned version. Fixed to 1.5.0, re-verified end to end — all six synthetic cases passing, clean exit codes at every step.

What kept getting re-learned

01

Extraction is fact. Code is judgment.

The moment a threshold or a flag lived inside the model's schema, it got inconsistent. Every derived decision moved to deterministic code, every time this was tested.

02

Never claim more than the code proves.

"Ready" became "human review required." "Immutable" became "per-run record." Two unrelated fixes, one rule.

03

Discovery before code.

The eight-question interview is what made the later scope cut correct instead of arbitrary — it named the actual success metric before any plan existed.

04

Prove it in a clean room.

A stale requirements.txt survived every local test run. Only a fresh venv caught it.

05

Governance is a constraint, not a report.

Privacy-minimization was designed into the trace schema before the first commit of it — not audited in afterward.
